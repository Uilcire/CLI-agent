# Assistant Memory — Code Review Report

Scope: classic code-review territory (correctness, idioms, naming, error handling, dead code). Threading, security, schema, and doc-drift are covered by sibling reviewers and intentionally skipped here.

## Summary

The module is structurally clean and the public surface matches the design doc. However the **single biggest issue is integration**: the entire two-stage retrieval pipeline (`RetrievalPipeline.retrieve` + `MAIN_RESPONSE_PROMPT`) is constructed but never invoked from anywhere in the codebase. The `cli/app.py` wiring only injects the static startup context (immutable_core + soul + user summary + current.md) into the system prompt; per-turn scope/file selection never runs, so the user's queries are answered without the retrieved memories the design depends on. This is a Critical-severity bug, not a code-style nit.

Beyond that: a handful of real defects in `_extract_learnings` and `_append_under_heading`, an off-by-one in section parsing in manager, several places that swallow exceptions too broadly, and a mix of `dict` vs `dict[str, Any]` typing inconsistencies.

## Critical Issues

### CR-01: Retrieval pipeline is wired but never called

**Files:** `src/agent/assistant_memory/manager.py:90`, `src/agent/cli/app.py:239-243`, `src/agent/assistant_memory/retrieval.py:113`, `src/agent/assistant_memory/prompts.py:61`

**Issue:** `AssistantMemoryManager.__init__` builds `self.retrieval = RetrievalPipeline(...)`, but no method on the manager ever calls `self.retrieval.retrieve(...)`. Searching the whole repo confirms `MAIN_RESPONSE_PROMPT`, `RetrievalPipeline.retrieve`, `select_scopes`, and `select_files` have zero call sites outside their definition. `app.py` calls `memory.on_startup` once (static context) and then `memory.on_user_turn` / `on_assistant_turn` after the LLM has already replied — retrieval is supposed to happen *before* the main LLM call to inject `file_contents` + `current_context` into the prompt, per design Stage 3.

Effect: the assistant answers every query with only the boot-time context dump. The whole point of the design (per-query scope+file selection so 80% of personal queries get the right files) is non-functional.

**Fix:** Add a `prepare_turn(query) -> str` (or similar) on the manager that runs `self.retrieval.retrieve(query, self.recent_turns)`, formats `MAIN_RESPONSE_PROMPT`, and returns the augmented user message (or a system-message addendum). Call it from `app.py` immediately before `run_streaming(...)`. Also: append `on_user_turn(user_input)` *before* retrieval so recent_turns includes the current query, and consider whether the curator should still see the un-augmented user_msg (it should — pass the original query separately).

### CR-02: `_extract_learnings` skips heading-line content and over-captures

**File:** `src/agent/assistant_memory/curator.py:339-350`

**Issue:** Two bugs in the same function:

1. The `continue` after the `## ` line means even if the heading itself contained inline content (it shouldn't, but markdown allows it) it'd be skipped — minor. The real bug: there is **no termination** when a non-matching `##` heading is encountered. The `capture` flag is reset, but the loop only resets it when it sees another `## ` line. Sub-headers (`### foo`) fall under the previous `capture` value, which is correct, but more importantly **blank-line handling**: a blank line inside the captured section causes `if capture and line.strip():` to skip the blank, so output loses paragraph separation between bullets. Probably fine, but worth noting.

2. The substring match `"decision" in line.lower() or "fact" in line.lower() or "learn" in line.lower()` is brittle: a heading like `## What happened` would not capture, but `## Open threads — facts to revisit` would, despite being the wrong section. A digest with an unexpected heading wording silently drops learnings. This is a real failure mode because the digest is generated by the same LLM that is unreliable enough to need `_parse_json_object` fallbacks elsewhere.

**Fix:** Use the exact heading defined in `summarize_session`'s prompt (`## Decisions / facts learned`) for an exact-match start and stop on any subsequent `## `:

```python
def _extract_learnings(digest: str) -> str:
    start = "## Decisions / facts learned"
    if start not in digest:
        return ""
    after = digest.split(start, 1)[1]
    # stop at next H2
    end = re.search(r"\n##\s", after)
    section = after[: end.start()] if end else after
    return section.strip()
```

### WR-01: `_append_under_heading` doesn't actually insert under the heading

**File:** `src/agent/assistant_memory/curator.py:353-359`

**Issue:** The docstring says "Insert `content` under `heading` in `body`, creating the section if absent." When the heading exists, the implementation just appends to the **end of the file**, ignoring where the heading actually is. The inline comment admits this ("simpler than splicing") but the function name and docstring lie. If a project file has `## Learnings\n\n` followed by `## Recent Sessions\n...`, new learnings end up under "Recent Sessions", not "Learnings".

**Fix:** Either rename the function to `_append_to_body` and drop the "under heading" semantics, or actually splice:

```python
if heading in body:
    idx = body.index(heading)
    end = body.find("\n## ", idx + len(heading))
    insert_at = end if end != -1 else len(body)
    return body[:insert_at].rstrip() + "\n\n" + content.rstrip() + "\n" + body[insert_at:]
```

### WR-02: Description regex drops multi-line descriptions

**File:** `src/agent/assistant_memory/manager.py:61-63`

**Issue:**
```python
desc_match = re.search(r"##\s*Description\s*\n+([^\n#].*?)(?:\n##|\Z)", body, re.DOTALL)
if desc_match:
    description = desc_match.group(1).strip().splitlines()[0].strip() if desc_match.group(1).strip() else ""
```

The `[^\n#]` lookahead correctly skips a leading `#`, but then `.splitlines()[0]` immediately throws away every subsequent line of the description anyway. So a project with a 3-line description body shows only line 1 in the project view — possibly intentional (it's a "view"), but combined with the much more complex regex it suggests the author wanted multi-line and forgot. Either commit to single-line (drop the regex `re.DOTALL` and simplify) or actually return the full block.

Also: `[^\n#]` will reject a description that legitimately starts with `#` (a code-fence marker would already have been escaped, but what about `#1 priority: ...`?). Low-priority but worth a comment.

**Fix:** Simplify:
```python
m = re.search(r"##\s*Description\s*\n+([^\n].*)", body)
description = m.group(1).strip() if m else str(meta.get("description") or project_id)
```

### WR-03: `parse_frontmatter` silently drops malformed YAML

**File:** `src/agent/assistant_memory/schema.py:41-44`

**Issue:** `yaml.safe_load(meta_raw)` can raise `yaml.YAMLError` on malformed frontmatter. That isn't caught, so a corrupted file (manually edited and saved badly) crashes any caller — including the curator when it tries to read a file before appending. Combined with `read_file` returning `({}, "")` on missing files, callers can't distinguish "no frontmatter" from "broken frontmatter".

**Fix:**
```python
try:
    loaded = yaml.safe_load(meta_raw) if meta_raw.strip() else {}
except yaml.YAMLError:
    logger.warning("malformed frontmatter; treating as body-only")
    return {}, text
```

### WR-04: Atomic write isn't fully atomic across crashes

**File:** `src/agent/assistant_memory/store.py:25-29`

**Issue:** `tmp.write_text(...)` does not `fsync` before `os.replace`. On a power loss between write and replace the tmp file may exist with zero bytes; on a power loss after replace but before fsync of the directory, the rename may not be durable. For an assistant memory layer, durability of any single write isn't critical, but the function is named "atomic" — it's atomic against concurrent readers, but not against crashes. Worth a docstring caveat or a real `fsync` if you mean it. Not fixing this is fine; lying about it in the name isn't.

**Fix:** Either rename to `_safe_replace` or do:
```python
with open(tmp, "w", encoding="utf-8") as f:
    f.write(text)
    f.flush()
    os.fsync(f.fileno())
os.replace(tmp, path)
```

### WR-05: `apply_manifest_updates` substring match can hit the wrong line

**File:** `src/agent/assistant_memory/curator.py:196-200`

**Issue:** `if line_key in line:` matches any substring. If `line_key` is `alex.md` and the manifest happens to have `- **alexander.md** | ...` first, the wrong line gets replaced. The bug is symmetric with the `**alex.md**` key style used in `_append_manifest_line` (manager.py:273), which uses `f"**{project_id}.md**"` — that's the *right* pattern (delimiters anchor the match). The curator should do the same, and downstream curator-LLM `line_key` should match.

**Fix:** Normalize `line_key` to the bracketed form before matching, or do an exact regex:
```python
needle = line_key if line_key.startswith("**") else f"**{line_key}**"
if needle in line:
    ...
```

### WR-06: `propose_writes` and `apply_writes` use untyped `dict`

**File:** `src/agent/assistant_memory/curator.py:74-79, 117-121`

**Issue:** Signatures say `-> dict` and `proposal: dict`. With `from __future__ import annotations` already on top, you can use `dict[str, Any]` (or better, define a TypedDict or dataclass for the proposal shape — there's already `RetrievalResult` precedent in `schema.py`). Right now nothing constrains the structure; mypy can't catch a `proposal["writes"]` typo.

**Fix:** Use `TypedDict`:
```python
class WriteOp(TypedDict, total=False):
    file: str
    operation: Literal["append", "create", "update_field"]
    content: str
    layer: int
    field: str
    value: Any
class CuratorProposal(TypedDict):
    writes: list[WriteOp]
    manifest_updates: list[dict[str, str]]
```

### WR-07: Bare `except Exception` swallows everything in lifecycle methods

**File:** `src/agent/assistant_memory/manager.py:124, 135, 145, 190, 207, 232, 257, 286, 339`

**Issue:** Almost every public method on `AssistantMemoryManager` is wrapped in `try: ... except Exception: log.warning(...); return safe_default`. This is defensible at REPL boundaries — you don't want a memory bug killing the chat — but it also hides real bugs (a `KeyError` from a typo in code). At minimum, narrow:
- `on_startup` failure modes are I/O + YAML → catch `OSError, yaml.YAMLError`
- `find_project_for_cwd` → `OSError, ValueError`
- `handle_command` → narrow per branch

Also `on_assistant_turn` (line 145) catches and `return`s but only after the append-to-recent-turns step — meaning the curator thread is **not** spawned if appending failed. That's silent: a failed append means future curator runs will see stale recent_turns *and* the user will have no idea the memory layer skipped a turn.

**Fix:** Narrow at minimum to `(OSError, ValueError, yaml.YAMLError)`. Surface unexpected exceptions via `log.exception(...)` (you already do this in some, not others — be consistent).

### WR-08: `consolidate_session` forbidden-path check is too lenient

**File:** `src/agent/assistant_memory/curator.py:255-258`

**Issue:**
```python
if any(rel == fp or rel.startswith(fp) for fp in self._FORBIDDEN_PATHS):
```
`_FORBIDDEN_PATHS = ("identity/agent.md", "context/current.md")`. `rel.startswith("identity/agent.md")` matches both the forbidden file and *also* something like `identity/agent.md.bak` — not a real concern, but the bigger issue is the design doc says identity/me.md immutable fields should also be forbidden via `update_field` on protected keys. The current check only filters by path prefix, so a write op `{"file": "identity/me.md", "operation": "update_field", "field": "email", "value": "x"}` slips through as Layer 1.

**Fix:** Add `update_field` filtering for `identity/me.md` against a known immutable-field set, or push the policy check into `_apply_single`.

### WR-11: `extract_memory_notes` regex is greedy across multiple notes

**File:** `src/agent/assistant_memory/curator.py:22, 25-27`

**Issue:** `re.compile(r"\[memory note:\s*(.*?)\]", re.IGNORECASE | re.DOTALL)` — `.*?` is non-greedy, good. But `re.DOTALL` plus `]` as terminator means a memory note containing a `]` character (e.g. a JSON snippet or a markdown link `[x](y)`) gets cut at the first `]`. For arrays/dicts in notes that's fine; for prose mentioning `[brackets]` it breaks.

Note: this function is defined and exported but **never called anywhere** in the codebase. So it's dead code (see IN-01). Still, if you wire it up later, the regex is fragile.

**Fix:** Fence with a clearer delimiter (e.g. `[memory note: ...; end]`) or accept escaped brackets. For now, document the limitation.

### IN-06: `migrate_to_assistant_memory.py` swallows model_validate_json errors at process level only

**File:** `scripts/migrate_to_assistant_memory.py:128-129, 142-143, 156-157`

`Personality.model_validate_json(...)` and friends raise pydantic `ValidationError` on malformed JSON. The top-level handler catches `(FileNotFoundError, RuntimeError)` only — a single corrupt digest aborts the whole migration with an unhandled exception. For a one-shot migration script this might be desirable (loud failure), but at minimum log *which file* was being read when it died. Currently you get a traceback with no file context.

**Fix:**
```python
for path in sorted(digests_dir.glob("*.json")):
    try:
        d = SessionDigest.model_validate_json(path.read_text())
    except ValidationError as e:
        print(f"warning: skipping malformed digest {path}: {e}", file=sys.stderr)
        continue
    digests.append(d)
```

### IN-07: `print_mem_event` uses a module-level Console — interleaving with main display

**File:** `src/agent/cli/display.py:214, 217-227`

`_mem_console = Console()` is a separate Console instance from the one used inside `stream_assistant`. Rich's Live region uses its own console; concurrent prints from another Console can produce garbled output (especially during a Live update). Since memory events are emitted from the curator daemon thread (manager.py:167), this is a real race in interactive mode — orange MEMORY panels can land in the middle of a streaming markdown render and corrupt the Live region.

This crosses into the threading reviewer's territory but it's a display-layer choice that makes the race possible. Solution: queue mem events from threads and flush them only at known display-safe points (e.g., between turns).

**File:** `src/agent/assistant_memory/manager.py:50-55`

```python
if not s:
```

If `text` is `"---"` (only separators) you get `s = ""` → fallback. If `text` is `"a---"` → `s = "a"` → `s[:40].rstrip("-") = "a"`. Fine. Document or change.
